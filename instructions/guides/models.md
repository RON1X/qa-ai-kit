# GLM-5.3-Flash и DeepSeek V4.1 Flash: настройки и стиль работы

Для человека, который настраивает агента. Обоснования и источники — `research/07-deepseek-glm.md`.

## Настройки запроса
| | DeepSeek V4.1 Flash | GLM-5.3-Flash |
|---|---|---|
| temperature / top_p | 1.0 / 0.95 (в режиме рассуждения temperature игнорируется) | 1.0 / 0.95, менять только одно из двух |
| Рассуждение | включено по умолчанию; `reasoning_effort`: `none` выключает, `low`, `high`, `max` | всегда включено; `reasoning_effort`: `low`, `high`, `max` (по умолчанию `max`) |
| max_tokens | ≥ 32–64K: рассуждение и ответ делят один бюджет | то же |
| Особенности | `tool_choice: "required"` в режиме рассуждения → ошибка 400 | неизвестное значение `reasoning_effort` молча становится `max` |
| vLLM | `--tool-call-parser deepseek_v41 --reasoning-parser deepseek_v41 --enable-auto-tool-choice` | `--tool-call-parser glm47 --reasoning-parser glm47 --enable-auto-tool-choice` |

В Qwen Code уровень рассуждения для внутреннего сервера задавайте через `extra_body.reasoning_effort` (пример — `.qwen/settings.example.json`).
Низкая температура (0–0.1) для этих моделей не нужна: DeepSeek её игнорирует, GLM рекомендована 1.0.
Предсказуемость дают шаблоны, проверки и скрипты, а не температура.

## Сколько думать — по задаче
| Задача | reasoning_effort |
|---|---|
| Переименовать, отформатировать, мелкая правка, оглавление | `low` |
| Ручные кейсы, автотест по кейсу, API-тест | `high` |
| Разбор падения, спека большой задачи, изменение каркаса | `max` |

`reasoning_effort` меняет глубину рассуждения, а не длину видимого ответа. Длину ответа задаёт стиль (см. `response-style.md`).
`max_tokens` для сокращения ответа не используйте: модель не «сожмёт» ответ, а оборвётся на середине или потратит всё на рассуждение и вернёт пустой ответ.

## Кто что делает (гипотеза, проверьте контрольными задачами)
| Задача | Модель |
|---|---|
| Ручные кейсы по документации и скриншотам | GLM-5.3-Flash |
| Автотесты, разбор падений | DeepSeek V4.1 Flash |
| Ревью теста | **другая** модель, не та, что писала |

## Стиль работы, которого добиваемся
Эти правила уже есть в `AGENTS.md` и скиллах; здесь — зачем они.
1. **Маленькие шаги с проверкой.** План → код → компиляция → запуск → «испорченное ожидание» → 3 прогона. Длинные задачи модель упрощает и обрезает (опыт Сбера: сценарии 20+ шагов).
2. **Факты вместо догадок.** Локаторы — из снимка, колонки — из схемы, API — из контракта. Модель уверенно дописывает правдоподобное.
3. **Лимит попыток.** Не больше 3 итераций починки, потом отчёт человеку: модели склонны бесконечно «чинить», в том числе ослабляя проверки.
4. **Жёсткие ограничения — явно.** GLM лучше всего следует явным ограничениям («не менять pom.xml», «запусти тесты»), поэтому они вынесены в правила.
5. **Короткие инструкции.** Чем больше правил, тем больше пропусков: даже лучшие модели при сотнях инструкций выполняют около двух третей, и ранние инструкции выполняются лучше поздних. Важное — в начале `AGENTS.md`, детали — в скиллах.
6. **Один кейс — одна сессия.** Длинная сессия копит мусор в контексте; новая задача — новая сессия.

## Признаки неправильной настройки сервера
| Симптом | Причина |
|---|---|
| Вызов инструмента приходит текстом (`<tool_call>`, теги DSML) | не включены `--tool-call-parser` и `--enable-auto-tool-choice` |
| Рассуждения перемешаны с ответом | не включён `--reasoning-parser` |
| Пустой ответ, `finish_reason=length` | мал `max_tokens` |
| Модель не видит скриншот | сервер запущен без зрения (у DeepSeek флаг `--language-model-only`) |
| GLM теряет нить в длинной сессии | `clear_thinking: false`, а клиент не возвращает рассуждения → `clear_thinking: true` |
