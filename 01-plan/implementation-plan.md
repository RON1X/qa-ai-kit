# План внедрения: ИИ-помощник для ручных кейсов и UI e2e автотестов

**Цель.** Внутри закрытого контура сделать рабочий инструмент: внутренняя модель по документации пишет
ручные тест-кейсы, по кейсам — Java + Playwright автотесты с проверками в БД и стабами SberMock,
помогает разбирать падения. Человек принимает решения и ревьюит; модель делает черновую работу.

**Продукт на выходе** — не отдельное приложение, а **репозиторий автотестов, который «понимает» агент**:
`AGENTS.md` + скиллы + команды + субагент-ревьюер + документы-контекст + скрипты-ограничители.
Работает в Qwen Code (или любом агенте с поддержкой AGENTS.md/SKILL.md); в крайнем случае — через чат.

**Ориентир по срокам** — один инженер, 6 недель до пилотных метрик. Фазы 1–2 можно вести параллельно.

## Принципы (из ресерча)
1. **Сначала эталон, потом генерация.** Модель копирует паттерны репозитория — включая плохие. Каркас и 2–3 эталонных теста пишет человек.
2. **Контекст важнее модели.** Архитектурный README, схема БД, каталог интеграций, оглавление методов.
3. **Маленькие шаги с проверкой.** План → код → компиляция → запуск → «докажи, что падает» → ревью. Лимит 3 итерации.
4. **Механические правила — скриптом**, суждения — инструкцией.
5. **Человек на гейтах:** одобряет план, ревьюит код, решает «баг продукта или теста».
6. **Мерить пользу, а не количество.**

## Фаза 0. Разведка и доступы (неделя 1)
- [ ] Модели: DeepSeek V4.1 Flash и GLM-5.3-Flash — `served-model-name`, `max-model-len`, включены ли парсеры инструментов и рассуждений, зрение, лимиты запросов. Вопросы к платформенной команде — в конце `00-research/07-deepseek-glm.md`.
- [ ] Агент: можно ли поставить Qwen Code (Node.js 22+, зеркало npm) или есть только чат/IDE-плагин.
- [ ] Зеркала: Nexus (версии из `03-java-examples/pom.xml`), npm (`@qwen-code/qwen-code`, `@playwright/mcp` или `@playwright/cli`), браузеры Playwright.
- [ ] БД стенда: два пользователя — только SELECT для проверок и ограниченная запись для уборки; тип БД (PostgreSQL/Oracle).
- [ ] SberMock: есть ли API для создания/удаления стаба и чтения журнала, условия на тело, приоритеты, изоляция. Заполнить раздел в `docs/integrations.md`.
- [ ] Фронт: договориться об атрибуте `data-qa` для элементов без доступного имени (таблицы, иконки).
- [ ] TMS: где живут ручные кейсы (Markdown в репозитории, Allure TestOps, Test IT) и как связывать с автотестами (`@TmsLink`/`@AllureId`).
- [ ] Базовые метрики «до»: сколько времени занимает кейс и автотест сейчас, доля флаки в прогоне.
- [ ] Политика: разрешено ли заносить open source (Superpowers — MIT, Playwright MCP — Apache-2.0) и отправлять код/данные во внутреннюю модель.

**Готово, когда:** известны модель и агент, есть доступы к БД и API SberMock (или понятно, что API нет), версии зависимостей есть в Nexus.

## Фаза 1. Каркас фреймворка — пишет человек (недели 1–2)
Перенести из `03-java-examples` и адаптировать под ваш проект:
- [ ] `core/`: `PlaywrightExtension` (контекст на тест, трасса при падении в Allure), `AuthState`, `Config`, `TestData`, `Attach`, `Cleanup`.
- [ ] `db/`: `Db` (пулы ro/rw, SQL из файлов, логирование в Allure) + первый DAO.
- [ ] `mock/`: `MockServer`, `Stub`, `Mocks`; **адаптер `SberMockClient` по документации SberMock** (все `TODO(SberMock)`). Если API нет — вариант с заранее заведёнными «говорящими» ключами (см. `docs/integrations.md`).
- [ ] Перевести существующие тесты на `assertThat` без пауз (иначе модель скопирует паузы).
- [ ] 2–3 **эталонных теста** по образцу `CreatePilotTest`: позитив с БД и интеграцией, негатив по интеграции, валидация с границами.
- [ ] `junit-platform.properties` (параллельность классов), Allure + AspectJ в Surefire.

**Готово, когда:** эталонные тесты зелёные 5/5 прогонов подряд и падают при испорченном ожидании.

## Фаза 2. Контекст для агента (неделя 2)
- [ ] Скопировать `02-agent-kit` в корень репозитория, заполнить все `[ЗАПОЛНИТЬ]`.
- [ ] `docs/architecture.md` — сгенерировать агентом по шаблону, вычитать, закоммитить (опыт Росгосстраха: 40 минут вместо двух недель исправлений).
- [ ] `docs/db-schema.md` — `scripts/db-schema-to-md.sql` + значения статусов + примеры строк.
- [ ] `docs/integrations.md` — все интеграции раздела, с которого начинаете: путь, ключ корреляции, ответы, таймаут.
- [ ] `docs/framework-index.md` — `scripts/index-framework.sh`.
- [ ] `docs/snapshots/` — aria-снимки ключевых страниц раздела.
- [ ] `.qwen/settings.json` по примеру; телеметрия и автообновление выключены.
- [ ] Прогнать **контрольные задачи** из `02-agent-kit/README.md`, записать ошибки модели, дописать правила в скиллы.

**Готово, когда:** контрольные задачи 4–6 (не ослаблять тест, ловить паузу на ревью, отказ от массового DELETE) модель проходит.

## Фаза 3. Ручные тест-кейсы (неделя 3)
- [ ] Выбрать один подраздел (например, «Пилоты / Добавление»), дать документацию и скриншоты, `/tc`.
- [ ] Ревью кейсов человеком: принят как есть / с правками / отклонён — записывать.
- [ ] Вопросы из раздела «Чего нет в требованиях» — отправить аналитику (это отдельная ценность: ранний поиск дыр в требованиях).
- [ ] Дописать в `guidelines.md` то, что модель систематически упускает (банковская специфика, роли, аудит).

**Готово, когда:** ≥ 60% кейсов принимаются без правок или с мелкими правками.

## Фаза 4. Автотесты по кейсам (недели 3–5)
- [ ] 10 кейсов пилотного подраздела → `/automate` по одному. Не пачкой: один кейс — одна сессия.
- [ ] На каждый тест: план одобрен → компиляция → запуск → «докажи, что падает» → 3 прогона → `test-reviewer` → ревью человека.
- [ ] `scripts/guard-tests.sh` в CI на merge request.
- [ ] Записывать по каждому тесту: итераций до зелёного, правок человека, найденных багов продукта, время.

**Готово, когда:** ≥ 60% автотестов принимаются с мелкими правками, флаки после недели прогонов < 5%.

## Фаза 5. Разбор падений и сопровождение (неделя 5–6)
- [ ] Ночной прогон → по каждому падению `/debug-test` → классификация (продукт / тест / данные / мок / стенд / загрязнение).
- [ ] Баги продукта — по шаблону из `test-debugging`; тест не трогать.
- [ ] Ночной «уборщик» данных прогона (по маркеру `AT-`, с лимитом и dry-run) как страховка.
- [ ] Включить `Tracing.StartOptions.setAriaSnapshots(true)` (Playwright 1.63) — трасса станет источником реальных локаторов для починки.

## Фаза 6. Масштабирование (дальше)
- [ ] Остальные разделы: Симуляции → Внедрения → История изменения. Для каждого: интеграции в каталог, эталонный тест, снимки.
- [ ] Обновление `docs/architecture.md` раз в 1–2 месяца, `framework-index.md` — на каждом мерже.
- [ ] API-уровень для интеграций (все коды ошибок) — разгрузить UI e2e.
- [ ] Связка с TMS: импорт `.md`-кейсов в Allure TestOps / Test IT через их API или MCP (у Allure TestOps он встроен с 26.1.1).

## Метрики
| Метрика | Как считать | Ориентир |
|---|---|---|
| Кейсы приняты без правок / с мелкими | ревью человека | ≥ 60% (у Сбера 68% для автотестов) |
| Автотесты приняты с мелкими правками | ревью человека | ≥ 60% |
| Итераций до зелёного | отчёт агента | ≤ 3 |
| Флаки | падения без изменений кода за неделю | < 5% |
| Время на кейс / автотест | до и после | −30…50% (Совкомбанк, Яндекс) |
| Баги продукта, найденные автотестами | баг-трекер | растёт |
| Вопросов к требованиям | раздел «Чего нет в требованиях» | — (ранний поиск дыр) |

## Риски (то, что вероятнее всего «укусит»)
| Риск | Признак | Что делать |
|---|---|---|
| Модель выдумывает локаторы | тест падает на «элемент не найден», имена похожи, но не те | снимки страниц в контексте, `TODO(locator)`, codegen |
| Модель «чинит» тест, ослабляя проверки | удалённые `assertThat`, `contains` вместо `equals` | правило 3, `guard-tests.sh`, ревьюер, человек |
| У SberMock нет API или нет изоляции | стабы мешают друг другу | «говорящие» ключи, отдельный инстанс на команду, приоритеты |
| Мало контекста у модели | обрывает длинные тесты, забывает правила | короче `AGENTS.md`, один кейс за сессию, `framework-index.md` вместо всего репозитория |
| Общий стенд нестабилен | падения без изменений кода | классификация в `test-debugging`, трассы, не лечить паузами |
| Ревью становится узким местом | очередь MR | субагент-ревьюер до человека; чек-лист; маленькие MR |
| Люди не пользуются | инструмент есть, задач нет | обучение, готовые команды `/tc`, `/automate`, демо на реальном баге |
