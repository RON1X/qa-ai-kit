# Spec-Driven Development и спеки для автотестов

Вопрос: строить ли инструкции для автотестов по SDD (спека → план → задачи → код) и как писать спеки.
Короткий ответ: **брать spec-first в облегчённом виде** — короткая спека для больших задач, ручной кейс как спека
для одного теста, без тяжёлых инструментов. Обоснование ниже.

## Что такое SDD
Спека пишется до кода и служит источником правды и для человека, и для ИИ. Это структурированный документ о поведении
на естественном языке, близкий к PRD. Birgitta Böckeler (Thoughtworks, martinfowler.com, 15.10.2025) выделяет три уровня:
- **spec-first** — спека пишется под задачу и используется в ней;
- **spec-anchored** — спека сохраняется и поддерживается вместе с фичей;
- **spec-as-source** — человек правит только спеку, код генерируется и руками не трогается.

По её наблюдению, все инструменты — spec-first, а дальше идут немногие.

## Инструменты
| Инструмент | Артефакты | Поток | Особенности |
|---|---|---|---|
| **Kiro** (AWS) | `requirements.md`, `design.md`, `tasks.md`; «steering»: `product.md`, `structure.md`, `tech.md` | требования → дизайн → задачи → выполнение | требования в нотации **EARS**: «WHEN [условие] THE SYSTEM SHALL [поведение]»; каждое требование должно напрямую превращаться в тест-кейс |
| **GitHub Spec Kit** | `constitution.md` (неизменяемые принципы), спека из нескольких файлов, план, задачи, чек-листы | Constitution → Specify → Plan → Tasks (slash-команды) | ветка на каждую спеку; много markdown |
| **Tessl** | спека на каждый файл кода, теги `@generate`, `@test` | spec-as-source | закрытая бета; сгенерированный код помечен «не править» |
| **OpenSpec** | `openspec/specs/` (текущее поведение) и `openspec/changes/` (предложение изменения: proposal, tasks, дельты спек) | предложение → задачи → применение → архивирование | ориентирован на изменения в существующем коде |
| **Playwright Test Agents** | `specs/*.md` — план тестов; `seed.spec.ts` — пример теста | planner → generator → healer | план: обзор приложения, сценарии с шагами и ожидаемыми результатами; только TypeScript |

## Критика (почему не брать SDD-инструмент целиком)
Из статьи Böckeler и Thoughtworks Technology Radar (SDD в кольце **Assess**, ноябрь 2025):
- **Не по размеру задачи.** Kiro превратил небольшой баг в 4 пользовательские истории и 16 критериев приёмки — «кувалда для ореха».
- **Ревью markdown тяжелее ревью кода.** Spec Kit порождает много многословных повторяющихся файлов: «я бы лучше ревьюила код, чем все эти markdown-файлы».
- **Ложное чувство контроля.** Агент всё равно игнорировал инструкции: создавал дубли существующих классов или чрезмерно применял правила «конституции».
- **Неясно, где граница функционального и технического** в спеке.
- Thoughtworks: длинные спеки трудно ревьюить, неясно, для кого они; есть риск заново выучить «горький урок» — вручную написанные детальные правила для ИИ не масштабируются.

Что Böckeler считает ценным: **сама привычка структурировать задачу до промпта**, гибкость под размер задачи,
итеративность маленькими шагами, удобное ревью спеки.

## Применение к автотестам
В тестировании спека уже существует: **ручной тест-кейс** — это спека одного теста (предусловия, шаги, ожидаемые
результаты, данные), а требования с критериями приёмки — спека раздела. Поэтому:

| Размер задачи | Что служит спекой | Инструмент в наборе |
|---|---|---|
| Один автотест | ручной кейс `test-cases/.../TC-NNN.md` | `ui-tests`, `api-tests` |
| Раздел, 3+ теста, новый PO/клиент | короткая `specs/<раздел>-<задача>.md` | `test-spec` |
| Изменение каркаса | спека с разделом «как не сломать существующие тесты» | `test-spec` |
| Починка теста | улики и причина, не спека | `test-debugging` |

### Как писать проверяемые требования
- **EARS** (Kiro): «КОГДА <событие/условие> СИСТЕМА ДОЛЖНА <наблюдаемое поведение>» — одна строка, одно поведение, сразу превращается в проверку.
- **Дано / Когда / Тогда** — для сценариев из нескольких шагов (так пишет требования Kiro и BDD).
- Наблюдаемый результат: текст сообщения, статус, запись в БД, поле запроса — а не «работает корректно».
- Чего нет в требованиях — в «Открытые вопросы», а не додумывается моделью.
- В плане тестов Playwright planner каждый сценарий содержит шаги и **ожидаемые результаты**, и ссылку на seed-тест (пример, на который равняться) — у нас это эталонные тесты в `AGENTS.md`.

### Чего в спеке не нужно
Обзора архитектуры, общих правил, кода реализации. См. `09-writing-instructions.md`: обзоры в контекстных файлах
агентам не помогают, а удорожают работу.

## Итог для набора
- Новый скилл `test-spec` и команда `/spec`: короткая спека с целью, «входит / не входит», критериями AC в EARS,
  таблицей тестов со строкой «Ловит», данными и открытыми вопросами. Одобрение человека — до кода.
- Для одного теста спека не нужна: ручной кейс + план-таблица в начале скилла `ui-tests`/`api-tests`.
- Ревьюер (`test-reviewer`) сверяет тест со спекой и кейсом.
