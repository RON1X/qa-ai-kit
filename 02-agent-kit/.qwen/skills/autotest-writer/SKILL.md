# Автотест по ручному кейсу

Ты пишешь UI e2e тест для общего стенда банковской админки. Главная ценность теста — он **падает,
когда продукт сломан**, и **не падает, когда продукт в порядке**. Зелёный тест, который не может
упасть, хуже отсутствующего: он создаёт ложную уверенность.

## Железный закон

```
НЕ ВЫДУМЫВАТЬ ЛОКАТОРЫ, ПОЛЯ БД И API МОКОВ.
НЕ СДАВАТЬ ТЕСТ, ПОКА НЕ ВИДЕЛ, КАК ОН ПАДАЕТ НА СЛОМАННОМ ОЖИДАНИИ.
```

## Шаги

### 1. Прочитай контекст (без этого не начинай)
- Ручной кейс (путь дан в задаче).
- `AGENTS.md`, `docs/architecture.md`.
- Эталон `tests/pilots/CreatePilotTest.java` и существующие Page Object-ы нужного раздела.
- Если в кейсе есть «сохранено / статус / история» — `docs/db-schema.md`.
- Если шаг вызывает внешнюю систему — `docs/integrations.md`.

### 2. Составь план и покажи его
Таблица — одна строка на шаг кейса:

| Шаг кейса | Действие в тесте | Проверка | Уровень (UI / БД / мок) | Есть метод? (какой) или новый |
|---|---|---|---|---|

Ниже таблицы — строка `Ловит: <какой дефект продукта поймает тест>`.
Если шагов больше 15 или в кейсе несколько независимых поведений — предложи разбить на несколько тестов
и не продолжай без ответа.

### 3. Добудь настоящие локаторы
Для каждого нового элемента — по порядку, до первого успеха (подробно в `references/locators.md`):
1. Уже есть в Page Object → используй.
2. Aria-снимок страницы (`playwright-cli snapshot`, Playwright MCP `browser_snapshot` или сохранённый снимок в `docs/snapshots/`).
3. Codegen: `mvn exec:java -e -D exec.mainClass=com.microsoft.playwright.CLI -D exec.args="codegen --target java <url>"`.
4. Ничего недоступно → `// TODO(locator): <что ищем, на какой странице>` и вопрос человеку.

Приоритет: `getByRole` с именем → `getByLabel` → `getByText` → `getByTestId` → CSS (только с комментарием, почему иначе нельзя).
Запрещены: XPath по структуре, `nth()` без причины, классы стилей (`.btn-primary`, `.css-1x2y3z`).

### 4. Данные, моки, БД
- Данные: `XxxData.valid().withПоле(...)` — меняй только то, что проверяет тест.
- Внешняя система в сценарии → стаб через скилл `integration-mocks`. Correlation key — уникальное значение из данных теста.
- Кейс говорит «сохранено / изменился статус / запись в истории» → проверка в БД через скилл `db-checks`.
- Уборка: `cleanup.add(...)` регистрируется **до** действия, которое создаёт данные.

### 5. Напиши тест по шаблону `references/test-template.md`
- `@DisplayName` = название кейса, `@TmsLink` = путь к кейсу, javadoc со строкой `Ловит:`.
- Порядок в теле: подготовка → действие → проверки UI → проверки БД → проверки исходящих запросов.
- Ожидаемые значения — литералы из кейса.

### 6. Цикл компиляции и запуска (не больше 3 итераций)
1. `mvn -q test-compile` → исправь ошибки компиляции.
2. Запусти тест. Упал — **не правь проверки**. Иди по скиллу `test-debugging`: сначала причина, потом правка.
3. После 3 неудачных итераций — стоп. Отчёт: что пробовал, вывод последнего запуска, гипотеза.

### 7. Докажи, что тест ловит дефект (обязательно)
Тест должен хотя бы раз упасть «по делу». Выбери ключевую проверку и временно испорти **ожидание**:
- UI: ожидаемый текст `"Черновик"` → `"Активен"`;
- БД: ожидаемый статус `"DRAFT"` → `"ACTIVE"`;
- мок: подмени стаб успеха на `serverError(...)`.

Запусти: тест обязан упасть, и сообщение должно объяснять, что не так. Верни как было, запусти снова — зелёный.
Если при испорченном ожидании тест остался зелёным — проверка не работает. Чини проверку, а не ожидание.

### 8. Проверка на флаки
`scripts/flaky-check.sh <Класс> 3` — три прогона подряд. Хотя бы одно падение → скилл `test-debugging`.

### 9. Ревью
Передай тест субагенту `test-reviewer` (или выполни чек-лист `test-review` сам). Исправь всё критичное.

### 10. Отчёт человеку
```
Тест: <путь>#<метод>   Кейс: <путь к кейсу>
Ловит: ...
Компиляция: OK
Прогоны: 3/3 зелёные (команда: ...)
Проверка «может упасть»: испортил <что> → упал с «<сообщение>» → вернул → зелёный
Новые/изменённые файлы: ...
TODO и вопросы: ...
```

## Частые ошибки, которые надо ловить у себя

| Мысль | Что на самом деле |
|---|---|
| «Локатор очевиден, проверять не надо» | Модель угадывает локаторы по похожим сайтам. Сверься со снимком. |
| «Подожду 2 секунды — и стабильно» | Пауза прячет гонку, а не устраняет её. Жди условие. |
| «Поменяю equals на contains — пройдёт» | Это ослабление проверки. Пройдёт и на сломанном продукте. |
| «Тест упал, значит тест неправильный» | Сначала докажи. Может быть, ты нашёл баг. |
| «Проверю, что строка есть в БД» | Проверяй поля, которые важны по кейсу: статус, суммы, автор, связи. |
| «Проверю, что мок вызван» | Проверяй, **что** система отправила: ключевые поля тела запроса. |
