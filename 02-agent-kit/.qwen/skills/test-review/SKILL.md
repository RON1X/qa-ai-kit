# Ревью автотеста

Ревью отвечает на один вопрос: **упадёт ли этот тест, если продукт сломается так, как описано в кейсе,
и останется ли он зелёным, если продукт в порядке?** Стиль и красота — вторичны.

Лучше всего ревью делает субагент `test-reviewer` со свежим контекстом: автор теста склонен
верить своему коду. Если субагента нет — пройди чек-лист сам, перечитав кейс заново.

## Вход
- Путь к тесту (и к изменённым PO/DAO/стабам), путь к ручному кейсу.
- `git diff` изменений.

## Чек-лист

### A. Ловит ли тест дефект (критично)
- [ ] Есть `Ловит: ...`, и тест действительно это проверяет.
- [ ] Каждый ожидаемый результат кейса превращён в проверку. Пропущенный ожидаемый результат — дефект ревью.
- [ ] Ожидаемые значения — литералы из кейса, а не значения, вычисленные тем же кодом или прочитанные из UI/БД и сравненные сами с собой.
- [ ] Нет проверок мока (стаб вернул X → «проверили», что вернулось X).
- [ ] Негативные проверки («не сохранено», «ошибки нет») стоят после доказательства, что событие произошло.
- [ ] В отчёте автора есть шаг «испортил ожидание → упал → вернул».

### Б. Стабильность (критично)
- [ ] Нет `Thread.sleep`, `waitForTimeout`, `NETWORKIDLE`, «магических» таймаутов без комментария.
- [ ] UI-проверки через `assertThat(locator)`; БД и моки — через `await`.
- [ ] Данные уникальны (`TestData.unique`), нет зависимости от порядка тестов и от «последней записи».
- [ ] Уборка зарегистрирована до действия; стабы — с ключом; нет глобального reset.
- [ ] Прогон 3/3 подтверждён выводом команды.

### В. Локаторы (важно)
- [ ] Каждый новый локатор подтверждён снимком/кодом/codegen или помечен `TODO(locator)`.
- [ ] Нет XPath по позиции, классов стилей, `nth()` без комментария.
- [ ] Локаторы ищутся внутри контейнера (диалог, строка), а не по всей странице.

### Г. Структура (важно)
- [ ] Одно поведение на тест; длина разумная (кейс > 15 шагов — разбит).
- [ ] Проверки в тесте, не в Page Object.
- [ ] SQL в файле, колонки из `docs/db-schema.md`, запись только по id и `AT-`.
- [ ] `@DisplayName`, `@TmsLink` соответствуют кейсу.
- [ ] Не тронуты `core/*`, `SberMockClient`, `pom.xml` без запроса.

### Д. Мелочи
- [ ] Имена методов описывают поведение, а не `test1`.
- [ ] Нет закомментированного кода и отладочного вывода.

## Признаки «ложной зелени» (типичные для ИИ-тестов)
| Признак | Почему плохо |
|---|---|
| Проверка ослаблена после падения (`equals` → `contains`, удалён `assert`) | тест подогнан под поведение, а не под требование |
| `@Disabled` / удалённый тест «чтобы прошло» | дефект спрятан |
| Ожидание = значение, прочитанное из той же системы | тавтология, не может упасть |
| Проверка только «элемент виден» после действия | не отличает успех от ошибки |
| Проверка «строка в БД есть» | пропускает неверные поля |
| Проверка «мок вызван» без тела запроса | пропускает неверное сопоставление полей |
| Таймауты увеличены «на всякий случай» | маскирует медленную деградацию |

## Формат ответа
```
Вердикт: ГОТОВ / ДОРАБОТАТЬ / ПЕРЕПИСАТЬ

Критично (блокирует):
- <файл>:<строка> — <что не так> — <как исправить>
Важно:
- ...
Мелочи:
- ...
Что хорошо:
- ...
Не проверял (и почему):
- ...
```
Последний раздел обязателен: ревьюер честно говорит, что осталось за рамками.
