# Правила покрытия и тест-дизайна

## 1. Как разбивать фичу на кейсы
1. Выпиши из документации все **правила** (валидации, условия, права, переходы статусов, интеграции).
2. Для каждого правила примени подходящую технику (раздел 2). Каждый кейс получает поле «Техника».
3. Сгруппируй: один кейс = одно проверяемое поведение. Не склеивай позитив и негатив.
4. Пройди чек-лист покрытия (раздел 3).
5. Составь раздел «Чего нет в требованиях» (раздел 5) — он идёт в итоговый ответ, а не в файлы.

## 2. Техники тест-дизайна (применяй, а не перечисляй)

**Классы эквивалентности** — для каждого поля: допустимые и недопустимые группы значений; из каждой группы один представитель.
> «Процент охвата» (целое 1–100): `<1` | `1..100` | `>100` | дробное | не число | пусто.

**Граничные значения** — значения на границе и рядом: `min-1, min, max, max+1`.
> Охват: `0` ✗, `1` ✓, `100` ✓, `101` ✗. Длина названия до 100 символов: 100 ✓, 101 ✗. Пробелы в начале/конце.

**Таблица решений** — когда результат зависит от комбинации условий.
> Раскатка разрешена, если: стратегия в статусе «Симуляция завершена» И роль «Администратор раскатки» И охват ≤ лимита продукта.
> 3 условия → до 8 строк; сокращай строки с одинаковым результатом, но оставляй каждое условие хотя бы раз ложным.

**Переходы состояний** — для жизненного цикла.
> Пилот → Симуляция → Внедрение → Откат. Покрой каждый допустимый переход и **запрещённые** (из «Черновика» сразу во «Внедрение»), а также повторное действие в том же статусе.

**Попарное тестирование** — когда параметров много (продукт × сегмент × роль × канал): каждая пара значений встречается хотя бы в одном кейсе. Пометь кейсы `Техника: Попарное`.

**Сценарий использования** — сквозной путь пользователя через несколько разделов (создать пилот → провести симуляцию → внедрить → увидеть в истории). Таких кейсов немного, приоритет высокий.

## 3. Чек-лист покрытия
- [ ] Основной позитивный сценарий
- [ ] Обязательные поля: каждое пустое по отдельности
- [ ] Границы и классы для каждого числового/текстового поля
- [ ] Формат и спецсимволы: кириллица, пробелы по краям, очень длинная строка, HTML-теги
- [ ] Дубликаты: уникальность имени/кода
- [ ] Роли: у кого действие есть, у кого кнопки нет / доступ запрещён
- [ ] Статусы: действие в каждом статусе, где оно разрешено и где запрещено
- [ ] Интеграции: успех, бизнес-ошибка, недоступность, таймаут внешней системы
- [ ] История изменения: действие отражено (кто, когда, что было → что стало)
- [ ] Откат/отмена: данные возвращаются, история фиксирует откат
- [ ] Параллельная работа: два пользователя редактируют одну сущность
- [ ] Отмена действия (кнопка «Отмена», закрытие модального окна): ничего не сохранено

## 4. Приоритеты
| Приоритет | Когда |
|---|---|
| Высокий | деньги и охват клиентов, права доступа, переходы статусов, раскатка/откат, основной сценарий |
| Средний | валидации полей, сообщения об ошибках интеграций, история изменения |
| Низкий | отображение, сортировки, тексты подсказок |

## 5. «Чего нет в требованиях» (обязательно в ответе)
Документация описывает, что система должна делать, но молчит о многом. Перечисли до 5 самых вероятных
пробелов в виде вопросов к аналитику, например:
- Что видит пользователь, если сервис сегментов не ответил за 30 секунд? Пилот сохраняется?
- Можно ли создать два пилота с одинаковым названием в разных стратегиях?
- Что происходит с запущенной симуляцией при откате стратегии?
Для таких мест создавай кейс с пометкой `<ожидаемый результат уточнить>`, а не выдумывай поведение.

## 6. Доменные подсказки: админка стратегий
- Жизненный цикл: пилот (ограниченный охват) → симуляция (расчёт на исторических данных) → внедрение (раскатка на продукт/сегмент) → история изменения (аудит, откат).
- Финансовые параметры: проценты > 100 и < 0, нулевые значения, точность (сколько знаков после запятой), разделитель `,` vs `.`.
- Охват: процент клиентов, сегменты, пересечение сегментов, лимиты продукта.
- Аудит: каждое изменение — кто, когда, старое и новое значение; откат — тоже запись.
- Роли: создать/редактировать/раскатить/откатить могут разные роли — проверяй каждую границу прав.

## 7. Анти-паттерны
| Плохо | Хорошо |
|---|---|
| «Проверить, что форма работает» | «Появилось уведомление “Пилот создан”» |
| «Ввести некорректные данные» | «В поле “Процент охвата” ввести `101`» |
| Десять проверок в одном кейсе | Один кейс — одно поведение |
| Ожидаемый результат придуман | `<уточнить>` + вопрос аналитику |
| Шаги зависят от предыдущего кейса | Всё нужное — в предусловиях |

| Поле | Значение |
|---|---|
| **Путь** | Пилоты/Добавление |
| **Требование** | ТЗ «Пилоты» п. 3.4 |
| **Приоритет** | Высокий |
| **Тип** | Негативный |
| **Техника** | Сценарий использования (ошибка интеграции) |
| **Роль** | Администратор стратегий |

## Предусловия
1. Пользователь авторизован с ролью «Администратор стратегий».
2. Сервис сегментов отвечает ошибкой 500 на проверку сегмента `AT_SEG_ERR01`.

## Шаги
| № | Действие | Ожидаемый результат |
|---|---|---|
| 1 | Открыть раздел «Пилоты» | Отображается таблица пилотов, кнопка «Создать пилот» |
| 2 | Нажать «Создать пилот» | Открылось окно «Новый пилот» |
| 3 | Заполнить поля данными из таблицы ниже | Ошибок валидации нет |
| 4 | Нажать «Сохранить» | Уведомление «Сервис сегментов недоступен. Попробуйте позже»; окно не закрылось, введённые данные сохранились в полях |

## Тестовые данные
| Поле | Значение | Комментарий |
|---|---|---|
| Название | AT-Пилот-ошибка-сегмента | уникальное |
| Стратегия | Кредитная стратегия v2 | существует на стенде |
| Продукт | Потребительский кредит | |

- Исходящий запрос: в сервис сегментов ушёл один запрос с `segmentCode = AT_SEG_ERR01`.
