# API-тест

API-тест проверяет то, что в UI проверять дорого: все коды ошибок, валидацию каждого поля, граничные значения,
права доступа, контракт ответа. UI-тесту остаётся сценарий пользователя.

## Слои (образец — пакет `api/` и `tests/api/pilots/PilotApiTest.java`)
| Слой | Класс | Что делает |
|---|---|---|
| Транспорт | `ApiClient` | сериализует тело через Jackson, прикладывает запрос и ответ в Allure, возвращает `ApiResponse` |
| Клиент раздела | `PilotApi extends ApiClient` | один метод = один эндпоинт; `createOk(...)` для подготовки данных |
| Модели | `api/model/*` (Lombok) | запросы и ответы ровно по контракту из `docs/api.md` |
| Фикстура | `ApiExtension` | `APIRequestContext` на тест с baseURL и авторизацией |
| Тест | `tests/api/<раздел>/*ApiTest` | проверки: статус → тело → БД |

## Правила
1. **Клиент не проверяет.** Методы клиента возвращают `ApiResponse` и не падают на 4xx/5xx — иначе негативный тест не написать. Падает только `createOk(...)` для подготовки данных.
2. **JSON — только Jackson.** Тело: `Json.toJson(body)` → `setData(String)` с `Content-Type: application/json` (уже в `ApiClient`). `RequestOptions.setData(объект)` не используй: Playwright сериализует его встроенным Gson и игнорирует `@JsonProperty`, `@JsonInclude`, `@Jacksonized`.
3. **Модели — Lombok.** `@Value @Builder(toBuilder = true) @Jacksonized`. Деньги и проценты — `BigDecimal`, даты без модуля jsr310 — `String`. Поля — по контракту, а не по тому, что читает тест: урезанная модель прячет ошибки.
4. **Негатив через toBuilder.** `validRequest().toBuilder().coveragePct(new BigDecimal("101")).build()`. Поле «не передано» — `null` (не сериализуется, `Json.MAPPER` настроен на NON_NULL). Битый JSON или неверный тип — `postRaw(path, "{...}")`.
5. **Порядок проверок:** статус (`then(response.status()).as("статус").isEqualTo(201)`) → тело → состояние в БД. Статус первым: иначе при 500 тест упадёт на разборе тела с непонятной ошибкой.
6. **Сравнение объектов:** `then(actual).usingRecursiveComparison().comparingOnlyFields(...)` или `.ignoringFields("id", "createdAt")`. Поля, которые генерирует система (id, даты, автор), проверяй отдельно и конкретно.
7. **Ожидания — из запроса или литералы**, не из того же ответа. `then(created.getName()).isEqualTo(body.getName())`, а не повторное чтение.
8. **Уборка.** После успешного создания — `cleanup.add(..., () -> api.delete(id))`. В негативных тестах — уборка по уникальному имени через БД: если API по ошибке примет запрос, мусор не останется.
9. **Ошибки API** — модель `ApiError`; проверяй код ошибки и поле, а не текст сообщения целиком (текст меняют чаще, чем код).

## Что покрывать для эндпоинта
| Группа | Примеры |
|---|---|
| Успех | создание, чтение, изменение, удаление; ответ совпадает с БД |
| Валидация | каждое обязательное поле пустое/не передано; границы `min-1, min, max, max+1`; неверный тип; лишнее поле |
| Бизнес-правила | дубликат, недопустимый переход статуса, ссылка на несуществующую сущность |
| Права | без авторизации → 401; роль без доступа → 403 |
| Идемпотентность | повторный DELETE, повторная отправка того же запроса |
| Контракт | обязательные поля ответа есть и правильного типа; формат ошибок единый |

Комбинации полей и кодов — параметризованным тестом (`@MethodSource` с комментарием, какой класс/границу проверяет строка).

## Шаги
1. Найди эндпоинт в `docs/api.md` (нет — попроси контракт: Swagger/OpenAPI, пример запроса и ответа). Готовые методы — в `docs/framework-index.md`.
2. Покажи план: таблица «проверка → запрос → ожидаемый статус → проверка тела/БД», строка `Ловит:`.
3. Модели и метод клиента — если их нет. Шаблон — `references/api-template.md`.
4. Тест, компиляция, запуск. Упал — скилл `test-debugging`, проверки не трогать.
5. Испорти ключевое ожидание (201 → 200, `"DRAFT"` → `"ACTIVE"`) — тест должен упасть. Верни.
6. `scripts/flaky-check.sh <Класс> 3`, `scripts/guard-tests.sh`, ревью (`test-review`).

## Подготовка данных для UI-тестов
UI-тест не должен кликать то, что не проверяет. Существующую сущность для редактирования создавай через
`new PilotApi(context.request()).createOk(...)`: так данные проходят ту же валидацию и попадают в историю изменений,
в отличие от прямого INSERT в БД.
