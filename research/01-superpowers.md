# Superpowers: как устроены написание тестов и поиск багов

Разбор по исходникам плагина Superpowers **v6.4.2** (автор Jesse Vincent, лицензия MIT), а не по пересказам.
Репозиторий: https://github.com/obra/superpowers

## Коротко
Superpowers — не инструмент тестирования, а **методология разработки для ИИ-агента**, упакованная в набор
скиллов (Markdown-инструкций `SKILL.md`). Агент сам решает, какой скилл подгрузить, по полю `description`.
Отдельного скилла «найди баги в приложении» в нём нет. Баги ловятся тремя механизмами:
1. **TDD** — тест пишется до кода и обязан упасть («красный»), иначе он ничего не доказывает;
2. **systematic-debugging** — строгий процесс поиска первопричины при любом падении;
3. **независимые ревьюеры** — субагенты со свежим контекстом проверяют работу против спецификации.

Плюс сквозное правило **verification-before-completion**: никаких заявлений «готово» без свежего вывода команды.

## Общий процесс
```
brainstorming → (worktree) → writing-plans → subagent-driven-development / executing-plans
                                              ├─ test-driven-development (на каждую задачу)
                                              ├─ requesting-code-review (после каждой задачи)
                                              └─ systematic-debugging (при любом падении)
→ verification-before-completion → finishing-a-development-branch
```
- **brainstorming** — до любого кода выясняет цель, пишет спецификацию, ждёт одобрения человека (жёсткий «гейт»).
- **writing-plans** — план из мелких задач: точные файлы, сигнатуры, тесты, команды проверки.
- **subagent-driven-development** — на каждую задачу свежий субагент-исполнитель, затем субагент-ревьюер.

## Как пишутся тесты (test-driven-development)

**Железный закон:** `NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST`. Код, написанный до теста, удаляется.

Цикл RED → GREEN → REFACTOR, где проверки обязательны:
- **Verify RED** — запустить тест и убедиться, что он падает *по правильной причине* (нет функции, а не опечатка). Тест сразу прошёл — он проверяет уже существующее поведение, переписать.
- **Verify GREEN** — прошёл не только свой тест, а весь набор проекта; вывод чистый, без предупреждений.

Отдельный файл `writing-good-tests.md` — самое ценное для QA. Два принципа:

**1. «Назови поломку» (Name the Break).** До написания тела теста ответь: *какое изменение в продукте
заставит этот тест упасть — и это баг или решение?*
- Нельзя назвать — тест не нужен или проверяет не то.
- Ожидаемое значение выводится независимо, литералом. Значение, посчитанное тем же кодом, — «зеркальная» проверка, всегда истинна.
- Нет «детекторов изменений»: тест на значение константы падает при редизайне и молчит при баге.

**2. «Проверяй настоящее» (Exercise the Real Thing).**
- Утверждение про мок ничего не говорит о продукте («тестируем поведение мока?»).
- Мокать только медленное/внешнее, понимая все побочные эффекты заменяемого.
- Ответ мока — полная копия реальной структуры, а не только поля, которые читает тест: урезанный мок проходит, а интеграция ломается.
- Сетап мока больше половины теста — переходи на интеграционный тест с настоящими компонентами.

**Мутационная проверка (в уме)**: мысленно сломай код — неверная константа, не та ветка, нет побочного эффекта,
пустой результат, нет проверки на ноль/пусто/нет прав. Хотя бы один тест должен упасть на каждую мутацию.

Список **тревожных признаков**: сетап и проверка используют один объект; тест падает только от краша или
отсутствующего селектора; ожидаемые значения спрятаны в циклах и билдерах; тест существует ради покрытия;
проверка `*-mock` test id.

## Как ищутся баги (systematic-debugging)

**Железный закон:** `NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST`.

Четыре фазы, переход только после завершения предыдущей:
1. **Root Cause Investigation** — прочитать ошибку целиком, стабильно воспроизвести, посмотреть недавние изменения,
   в многокомпонентной системе поставить диагностику **на каждой границе компонентов** и одним прогоном
   увидеть, где ломается; трассировать данные назад до источника (`root-cause-tracing.md`).
2. **Pattern Analysis** — найти похожий работающий код, сравнить построчно, выписать все различия.
3. **Hypothesis and Testing** — одна гипотеза «X — причина, потому что Y», минимальное изменение одной переменной.
4. **Implementation** — сначала падающий тест, воспроизводящий баг, потом одна правка в причину, затем проверка.

**Правило трёх попыток:** три неудачные правки подряд — стоп, это не неудачная гипотеза, а неверная архитектура;
обсудить с человеком. Сигналы человека «ты гадаешь», «а это точно происходит?» — вернуться в фазу 1.

Вспомогательные техники в папке скилла:
- **condition-based-waiting.md** — флаки-тесты лечатся ожиданием условия вместо `sleep`; пауза допустима, только если проверяется само время, и тогда с комментарием, откуда число. В реальной сессии автора: 15 флаки-тестов, проходимость 60% → 100%, прогон на 40% быстрее.
- **find-polluter.sh** — бисекция: прогоняет тесты по одному и находит тот, что оставляет «мусор» (файл, состояние), ломающий другие.
- **defense-in-depth.md** — после найденной причины добавить проверку на каждом слое, чтобы баг стал структурно невозможен.
- **root-cause-tracing.md** — разбор стека назад до места, где появилось плохое значение.

## Ревью и «доказательства вместо заявлений»
- **verification-before-completion**: «тесты проходят» требует вывода команды с 0 падений в этом же сообщении;
  «регрессионный тест работает» требует цикла *написал → прошёл → откатил фикс → упал → вернул → прошёл*;
  отчёт субагента «успех» не принимается без просмотра diff.
- **Ревьюер** (субагент) читает спецификацию как «документ видения»: если спецификация молчит о поведении,
  мерилом служит ожидание разумного пользователя; молчание — не разрешение ломаться. В конце ревьюер обязан
  перечислить, что он **не стал** оценивать и почему.
- **writing-plans → Review Focus**: в плане отдельно выписываются 5 входных данных/сбоев, которые спецификация
  подразумевает, но ни один тест не проверяет, — и к каждой добавляется тест.
- **writing-skills**: инструкции для агента тоже тестируются по TDD — сначала прогон сценария *без* скилла,
  фиксация того, как агент нарушает правило и какими словами оправдывается, затем скилл, закрывающий ровно
  эти лазейки. Отсюда в скиллах таблицы «Оправдание → Реальность» и «Красные флаги».

## Что из этого перенесено в набор для QA (`instructions`)
| Идея Superpowers | Как адаптирована для UI e2e |
|---|---|
| Verify RED: тест должен упасть | Шаг «Докажи, что тест ловит дефект»: временно испортить ожидание → тест падает с понятным сообщением → вернуть (продукт уже написан, поэтому ломаем ожидание, а не код) |
| Name the Break | Строка `Ловит: ...` в javadoc каждого теста; нет ответа — нет теста |
| Литералы вместо вычисленных ожиданий | Железное правило 9 в `AGENTS.md` |
| Не тестировать мок, полные ответы моков | Скилл `integration-mocks`: проверка тела исходящего запроса, полные тела стабов |
| systematic-debugging, 4 фазы, 3 попытки | Скилл `test-debugging` + классификация «продукт / тест / данные / мок / стенд / загрязнение» |
| condition-based-waiting | Таблица «вместо паузы» с эквивалентами Playwright, Awaitility и мок-журнала |
| find-polluter.sh | `scripts/find-polluter.sh` под Maven + JUnit 5 |
| verification-before-completion | «Определение готово» в `AGENTS.md`, отчёт с командой и выводом, 3 прогона подряд |
| Ревьюер со свежим контекстом | Субагент `test-reviewer` (только чтение) + скилл `test-review` |
| Review Focus | Раздел «Чего нет в требованиях» в генерации ручных кейсов |
| writing-skills: тестировать инструкции | «Контрольные задачи» в `instructions/README.md` |

## Можно ли занести сам Superpowers в закрытый контур
- Лицензия MIT — использовать и менять можно (сверьтесь с внутренней политикой по open source).
- Qwen Code поддерживается официально: `qwen extensions install obra/superpowers`. Без интернета — склонировать
  репозиторий снаружи и поставить из локальной папки или архива (`qwen extensions install <путь>`); Qwen Code
  умеет конвертировать плагины Claude Code.
- **Оговорки для локальной модели:** скиллы длинные и строгие (жёсткие гейты, субагенты на каждую задачу, ревью
  после каждой задачи). Это дорого по токенам и требует сильной модели, которая держит длинные инструкции.
  Для QA-задач полный цикл brainstorming → plan → subagents избыточен. Практичнее взять точечно:
  `systematic-debugging`, `verification-before-completion`, принципы `writing-good-tests.md` — что и сделано в наборе.
