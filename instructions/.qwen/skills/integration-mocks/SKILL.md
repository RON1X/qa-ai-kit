# Интеграции и стабы SberMock в UI e2e

Около трети функциональности админки — интеграции. В UI e2e внешняя система заменена стабом,
поэтому тест проверяет две вещи: **как админка ведёт себя при каждом ответе** и **что админка отправляет**.

## Железный закон

```
КАЖДЫЙ СТАБ — С КЛЮЧОМ ТЕСТА. НИКАКОГО ГЛОБАЛЬНОГО RESET.
API SBERMOCK НЕ УГАДЫВАТЬ.
```
Мок-сервер общий: стаб без ключа перехватит запросы чужих тестов, а reset удалит чужие стабы.
Если в `mock/SberMockClient.java` остались `TODO(SberMock)` — остановись: адаптер ещё не настроен человеком.

## Шаг 1. Найди интеграцию в каталоге
`docs/integrations.md`: какая система, какой путь, какой UI-сценарий её вызывает, какое поле запроса
служит ключом корреляции, какие ответы бывают. Интеграции нет в каталоге — спроси человека, не придумывай.

## Шаг 2. Выбери ключ корреляции
Браузер не может добавить заголовок в запрос, который бэкенд админки шлёт во внешнюю систему.
Поэтому ключ — **уникальное значение из данных теста**, которое админка пересылает дальше:
код сегмента, номер заявки, имя пилота. Генерируй его через `TestData.unique(...)` / `uniqueCode(...)`.

## Шаг 3. Стаб — через класс `<Система>Stubs`
Один класс на интеграцию (образец `mock/SegmentServiceStubs.java`). Метод на каждый ответ:
`valid(key)`, `notFound(key)`, `serverError(key)`, `timeout(key)`, `malformed(key)`.
- Тело ответа — полная копия реального ответа (все поля), а не только то, что читает тест.
- Таймаут = таймаут клиента админки + запас. Значение узнай у разработки и запиши в каталог.
- Новый метод добавляй в существующий класс, не создавай второй класс на ту же систему.

В тесте: `mocks.stub(SegmentServiceStubs.valid(pilot.getSegmentCode(), 120_000));` — удаление после теста сделает `Mocks.Extension`.

## Шаг 4. Проверь, что админка отправила
```java
RecordedRequest sent = mocks.awaitSingleRequest(SegmentServiceStubs.VALIDATE_PATH, pilot.getSegmentCode());
JsonNode body = Json.tree(sent.body());
then(body.path("segmentCode").asText()).isEqualTo(pilot.getSegmentCode());
then(body.path("productCode").asText()).isEqualTo("CONSUMER_LOAN");
```
Проверяй сопоставление «поле формы → поле запроса» литералами. Факт вызова без проверки тела почти ничего не доказывает.

## Шаг 5. Какие сценарии покрывать
Матрица — `references/case-matrix.md`. Минимум на каждую интеграцию в UI e2e:
1. Успех: UI показывает результат, данные сохранены, в запросе правильные поля.
2. Бизнес-ошибка внешней системы (4xx / код отказа): понятное сообщение пользователю, ничего не сохранено.
3. Техническая ошибка (5xx / разрыв соединения): деградация без «половинчатого» сохранения.
4. Таймаут: UI не висит бесконечно, сообщение, данные не сохранены (или сохранены со статусом «ожидает»).
Остальные комбинации кодов и полей — уровнем ниже (API-тесты), не в UI e2e.

## Что нельзя
- Проверять сам стаб: «стаб вернул 500» — это проверка мока, а не админки.
- Мокать в браузере (`page.route`) то, что вызывает бэкенд: браузер видит только свои запросы. `page.route` — только для UI-краёв (например, медленный ответ API самой админки).
- Делать стаб без ключа «на всякий случай» или с приоритетом ниже стабов по умолчанию.
