# Test Case Generator

Скилл превращает документацию (текст, ТЗ, описания, скриншоты) в готовые тест-кейсы в Markdown. Продукт — **банковская веб-админка** для проверки и раскатки банковских стратегий по продуктам на клиентов.

## Что делает скилл

1. Читает документацию, которую дал пользователь (текст и/или скриншоты).
2. Понимает, в какой раздел/папку складывать кейсы (пользователь задаёт структуру промтом).
3. Генерирует тест-кейсы — **каждый кейс это отдельный .md файл** по единому шаблону.
4. Раскладывает файлы в иерархию папок внутри `test-cases/`.

## Структура папок

Все кейсы лежат в `test-cases/`. Иерархию задаёт пользователь. Типовая структура:

```
test-cases/
├── Пилоты/
│   ├── Добавление/
│   │   ├── TC-001-добавление-валидные-данные.md
│   │   └── TC-002-добавление-пустые-поля.md
│   ├── Редактирование/
│   └── Список/
├── Симуляции/
├── Внедрения/
└── История изменения/
```

Правила по папкам:
- Корень — всегда `test-cases/`.
- Названия разделов и подразделов берутся ровно так, как назвал пользователь (включая русские названия и кириллицу).
- Если пользователь не указал подпапку — спроси один раз, в какой раздел класть, либо положи в корень соответствующего раздела.
- Не создавай лишних уровней вложенности, которые пользователь не просил. Вложенность переменная — может быть один уровень (`Симуляции/`) или несколько (`Внедрения/Раскатка/Сегменты/`). В шапке кейса поле **Путь** всегда отражает фактическую глубину.

## Именование файлов

Шаблон имени: `TC-<номер>-<краткое-описание-через-дефис>.md`

- `<номер>` — сквозной трёхзначный с ведущими нулями в рамках одной подпапки (`TC-001`, `TC-002`, ...).
- `<краткое-описание>` — строчными буквами, слова через дефис, без пробелов. Кириллица допустима.
- Перед созданием файла проверь существующие файлы в целевой папке (`ls`), чтобы продолжить нумерацию, а не перезаписать.

Пример: `TC-003-добавление-дубликат-имени-пилота.md`

## Шаблон тест-кейса

Каждый .md файл строится строго по шаблону из `references/template.md`. Прочитай его перед генерацией первого кейса. Кратко структура:

- Заголовок с ID и названием
- Метаданные: раздел, приоритет, тип (позитивный/негативный/граничный)
- Предусловия
- Шаги (нумерованная таблица: действие → ожидаемый результат)
- Тестовые данные
- Постусловия

## Как работать (пошагово)

1. **Получи вход.** Текст документации и/или скриншоты. Если есть скриншоты — опиши, что на них (поля, кнопки, состояния), и используй это для шагов.
2. **Уточни раздел**, если он не задан. Один вопрос, не больше.
3. **Прочитай** `references/template.md` и `references/guidelines.md`.
4. **Разбей фичу на кейсы.** Покрой: позитивные сценарии, негативные (валидация, ошибки), граничные значения, права доступа/роли, состояния данных. См. чек-лист покрытия в `references/guidelines.md`.
5. **Создай файлы.** Каждый кейс — отдельный .md по шаблону, в правильной папке, с корректной нумерацией.
6. **Покажи итог.** Список созданных файлов с путями.

## Покрытие для банковского домена

Учитывай специфику админки стратегий (детали в `references/guidelines.md`):
- Роли и права (кто может создавать/раскатывать/откатывать стратегию).
- Жизненный цикл: пилот → симуляция → внедрение → история.
- Раскатка на клиентов/продукты, проценты охвата, сегменты.
- Откат изменений и аудит (История изменения).
- Валидация финансовых параметров (границы, отрицательные значения, проценты >100).

## CLI / Qwen

Скилл рассчитан на запуск через CLI на базе Qwen. Поэтому:
- Не используй сложные внешние зависимости и скрипты — только чтение документации и запись .md файлов.
- Не генерируй код автотестов, если об этом прямо не попросили — только тест-кейсы в Markdown.
- Держи вывод детерминированным и предсказуемым.

## Reference files

- `references/template.md` — шаблон одного тест-кейса. Читай перед генерацией.
- `references/guidelines.md` — правила покрытия, приоритеты, доменные подсказки, пример заполненного кейса.
