# Проверки и данные в БД для UI e2e

БД стенда общая. Ошибка в запросе на запись портит данные другим людям, а проверка «строка существует»
пропускает половину дефектов. Поэтому: читаем аккуратно, пишем минимально, проверяем то, что важно.

## Железный закон

```
КОЛОНКИ И ТАБЛИЦЫ — ТОЛЬКО ИЗ docs/db-schema.md.
ЗАПИСЬ — ТОЛЬКО ПО ID И ПРЕФИКСУ AT-. НИКАКОГО TRUNCATE И МАССОВЫХ DELETE/UPDATE.
```
Нужной таблицы нет в `docs/db-schema.md` — остановись и попроси человека выгрузить схему (`scripts/db-schema-to-md.sql`).

## Когда проверять БД
- Кейс говорит «сохранено», «статус изменился», «запись в истории», «откат выполнен».
- UI показывает не всё, что важно бизнесу: автор, время, связи с другими сущностями, техполя статуса.
- Негатив: после ошибки интеграции/валидации **ничего не записалось** (половинчатое сохранение — частый дефект).

Не проверяй в БД то, что уже надёжно проверено в UI, и технические поля без бизнес-смысла.

## Как устроено (смотри `db/Db.java`, `db/PilotDb.java`)
1. **SQL-файл** `src/test/resources/sql/<раздел>/<что_делает>.sql`: явный список колонок, именованные параметры `:name`.
2. **Метод DAO** в `db/<Сущность>Db.java`: принимает параметры, возвращает `Optional<Row>` или `List<Row>`.
3. **record строки** с полями, которые нужны тестам. Перевод типов: `((Number) v).longValue()`, `new BigDecimal(v.toString())`, `((Timestamp) v).toLocalDateTime()`.
4. **В тесте** — только вызов DAO и `then(...)`.

## Асинхронность
Запись может появиться позже ответа UI. Никаких пауз:
```java
PilotRow row = await("пилот появился в БД").atMost(Duration.ofSeconds(15))
        .until(() -> pilotDb.findByName(name), Optional::isPresent)
        .orElseThrow();

await("запись в истории").atMost(Duration.ofSeconds(15)).untilAsserted(() ->
        then(pilotDb.history(row.id()))
                .extracting(HistoryRow::action, HistoryRow::actor)
                .containsExactly(tuple("CREATE", Config.adminLogin())));
```

## Негативная проверка «ничего не записалось»
Сначала докажи, что событие произошло (запрос ушёл во внешнюю систему, UI показал ошибку), и только потом
проверяй отсутствие записи. Иначе тест пройдёт и тогда, когда сохранение просто не успело начаться.

## Что проверять в строке
- Поля, которые ввёл пользователь (по литералам из кейса).
- Поля, которые вычисляет система: статус, автор (`created_by`), связи (id стратегии), суммы и проценты (`isEqualByComparingTo`).
- Историю/аудит: действие, автор, количество записей (ровно одна, а не «есть»).

## Подготовка данных
По умолчанию — через API или UI продукта: так проходят валидация, значения по умолчанию и запись в историю.
Прямой `INSERT` — только для состояний, которых нельзя достичь через продукт (например, «старая» запись),
и с комментарием, какие правила он обходит. Всегда с префиксом `AT-` и регистрацией уборки.

## Уборка
- Предпочтительно через API продукта (`APIRequestContext` из параметра теста).
- SQL-уборка — `where id = :id and name like 'AT-%'` (образец `sql/pilot/delete_test_pilot.sql`).
- Историю изменений и аудит не удаляем: это журнал.

## Продвинутое: «что именно изменило действие»
Для сложных сценариев (откат, массовая раскатка) удобна AssertJ-DB Changes — снимок до и после действия.
Образец и ограничения — `references/patterns.md`.

## Чек-лист
- [ ] Таблицы и колонки есть в `docs/db-schema.md`
- [ ] SQL в файле, колонки перечислены явно, параметры именованные
- [ ] Проверки через `Db.readOnly()`
- [ ] Асинхронная запись ожидается `await`, без пауз
- [ ] Проверены значимые поля, а не только факт наличия строки
- [ ] Уборка зарегистрирована до действия; запись — только по id и `AT-`
