# Спека перед кодом (spec-first для автотестов)

Короткий документ, о котором договариваемся **до** кода: что покрываем, что нет, какие тесты, на каком уровне,
какие данные и интеграции. Человек одобряет спеку — дальше код пишется по ней, а ревью сверяет код со спекой.

## Когда писать, а когда нет
| Задача | Спека |
|---|---|
| Один тест по готовому ручному кейсу | нет: кейс и есть спека, сразу скилл `ui-tests` / `api-tests` |
| Раздел целиком, 3+ теста, новый PO/клиент | да, короткая |
| Изменение каркаса (`core/`, расширения, конфиг) | да, с разделом «Как не сломать существующие тесты» |
| Исправление упавшего теста | нет: скилл `test-debugging` |

Не раздувай: спека на небольшую задачу — один экран. Длинную спеку человек не прочитает, а модель
не удержит; размер подбирай под задачу.

## Шаги
1. Собери вход: требования, ручные кейсы из `test-cases/`, `docs/api.md`, `docs/db-schema.md`, `docs/integrations.md`, готовые методы из `docs/framework-index.md`.
2. Напиши `specs/<раздел>-<задача>.md` по шаблону `references/spec-template.md`.
3. Покажи человеку: путь к файлу и 3–5 строк — что покрываем, сколько тестов, что вынесено за рамки, открытые вопросы.
4. Дождись одобрения или правок. Без одобрения код не пишем.
5. Реализуй по одной строке таблицы «Тесты» за раз (скиллы `ui-tests`, `api-tests`), отмечая `[x]`.
6. Поменялись требования по ходу — сначала правка спеки, потом кода.

## Как писать требования, чтобы их можно было проверить
Каждый критерий приёмки — проверяемое утверждение с условием и наблюдаемым результатом. Два удобных формата:
- **EARS**: `КОГДА <событие/условие> СИСТЕМА ДОЛЖНА <наблюдаемое поведение>`.
  «КОГДА сервис сегментов ответил 500, СИСТЕМА ДОЛЖНА показать “Сервис сегментов недоступен” и не сохранить пилот».
- **Дано / Когда / Тогда** — для сценариев из нескольких шагов.

Плохо: «форма работает корректно», «обработать ошибки». Хорошо: конкретное сообщение, статус, запись в БД, поле запроса.
Чего нет в требованиях — в «Открытые вопросы», а не додумывается.

## Чего в спеке не нужно
Пересказа архитектуры проекта и общих правил (они уже в `AGENTS.md` и скиллах), кода реализации, вариантов
«на будущее». Спека — решения, которые нельзя вывести из кода и требований.
