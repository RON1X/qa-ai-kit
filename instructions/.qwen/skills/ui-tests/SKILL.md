# UI-автотест по кейсу

Цель теста — **падать, когда продукт сломан, и не падать, когда он в порядке**. Зелёный тест,
который не может упасть, хуже отсутствующего: он создаёт ложную уверенность.

## Шаги

### 1. Контекст
Прочитай ручной кейс, `docs/framework-index.md` (что уже есть) и эталон `tests/ui/pilots/CreatePilotTest.java`.
Если в кейсе «сохранено / статус / история» — ещё `docs/db-schema.md`; если вызывается внешняя система — `docs/integrations.md`.

### 2. План — покажи до кода
| Шаг кейса | Действие | Проверка | Уровень (UI / БД / мок) | Метод: есть (какой) / новый |
|---|---|---|---|---|

Под таблицей — `Ловит: <дефект>`. Кейс длиннее 15 шагов или проверяет несколько поведений — предложи разбить.
Проверку, которую можно сделать через API быстрее и надёжнее (валидация полей, все коды ошибок), предложи вынести в API-тест.

### 3. Локаторы — только настоящие
Источник по порядку: существующий Page Object → aria-снимок страницы (скилл `playwright-browser`) → codegen
(`mvn exec:java -e -D exec.mainClass=com.microsoft.playwright.CLI -D exec.args="codegen --target java <url>"`) →
`// TODO(locator): <что, на какой странице>` и вопрос. Приоритет и примеры — `references/locators.md`.

### 4. Page Object — по правилам `references/page-object.md`
Коротко: PO отдаёт действия и локаторы, проверки — в тесте; повторяющиеся блоки (таблица, диалог, фильтры) —
компоненты; без глубокого наследования от BasePage; действия, после которых меняется экран, возвращают следующий PO.

### 5. Данные, моки, БД
- Данные формы: `XxxData.valid().toBuilder().поле(...).build()` — меняй только проверяемое поле.
- Данные, которые не относятся к проверке (существующая сущность для редактирования), создавай через API, а не кликами.
- Внешняя система → скилл `integration-mocks`. Запись в БД → скилл `db-checks`.
- `cleanup.add(...)` — до действия, которое создаёт данные.

### 6. Код теста — по шаблону `references/test-template.md`
`@DisplayName` = название кейса, `@TmsLink` = путь к кейсу, `@Severity` = приоритет кейса, `@Tag("ui")`, javadoc с `Ловит:`.
Порядок: подготовка → действие → проверки UI → БД → исходящие запросы. Ожидания — литералы из кейса.

### 7. Компиляция и запуск (не больше 3 итераций)
`mvn -q test-compile` → запуск теста. Упал — не трогай проверки, иди в скилл `test-debugging`.
После 3 неудачных итераций — стоп и отчёт: что пробовал, вывод последнего запуска, гипотеза.

### 8. Докажи, что тест ловит дефект
Временно испорти ключевое **ожидание** (`"Черновик"` → `"Активен"`, `"DRAFT"` → `"ACTIVE"`) и запусти:
тест обязан упасть с понятным сообщением. Верни, запусти — зелёный. Остался зелёным при испорченном
ожидании — проверка не работает, чини проверку.

### 9. Стабильность и ревью
`scripts/flaky-check.sh <Класс> 3`, затем `scripts/guard-tests.sh`, затем субагент `test-reviewer` или чек-лист `test-review`.

### 10. Отчёт (коротко)
```
Тест: <путь>#<метод> | Кейс: <путь>
Ловит: ...
Компиляция OK; прогоны 3/3 (команда: ...)
Испорченное ожидание: <что> → упал «<сообщение>» → вернул → зелёный
Файлы: ...
TODO и вопросы: ...
```

## Частые ошибки
| Мысль | На самом деле |
|---|---|
| «Локатор очевиден» | Модель угадывает по похожим сайтам. Сверься со снимком. |
| «Подожду 2 секунды» | Пауза прячет гонку. Жди условие: `assertThat(...).isVisible()`. |
| «Проверю, что элемент виден» | Не отличает успех от ошибки. Проверяй текст, значение, количество. |
| «equals → contains, и пройдёт» | Пройдёт и на сломанном продукте. |
| «Тест упал — значит тест неправ» | Сначала докажи. Может быть, это баг. |
| «Создам данные кликами в начале теста» | Медленно и хрупко. Готовь через API, кликай только проверяемое. |
