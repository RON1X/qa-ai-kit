# Проверки и данные в БД

БД стенда общая. Ошибка в запросе на запись портит данные другим людям, а проверка «строка существует»
пропускает половину дефектов. Поэтому: читаем аккуратно, пишем минимально, проверяем то, что важно.

## Главное
- Таблицы и колонки — только из `docs/db-schema.md`. Нужной таблицы там нет — попроси человека выгрузить схему (`scripts/db-schema-to-md.sql`), не угадывай.
- Проверки — `DbClient.readOnly()`. Запись — только подготовка и уборка через `DbClient.readWrite()`, по id и с `name like 'AT-%'`. `TRUNCATE` и массовые `DELETE`/`UPDATE` не используем: стенд общий.

## Когда проверять БД
- Кейс говорит «сохранено», «статус изменился», «запись в истории», «откат выполнен».
- UI или API показывают не всё важное: автор, время, связи, служебный статус.
- Негатив: после ошибки ничего не записалось (половинчатое сохранение — частый дефект).

Не дублируй в БД то, что надёжно проверено в UI или в ответе API.

## Как устроено (образец — `db/DbClient.java`, `db/PilotDb.java`)
1. **SQL-файл** `src/test/resources/sql/<раздел>/<что_делает>.sql`: явный список колонок, параметры `?`, комментарий с перечнем параметров.
2. **Метод DAO** в `db/<Сущность>Db.java`: `db.queryOne("pilot/find_by_name.sql", PilotRow::from, name)` → `Optional<Row>`, `db.query(...)` → `List<Row>`.
3. **Строка — Lombok `@Value @Builder`** со статическим `from(ResultSet rs)`. Типы: `rs.getLong`, `rs.getBigDecimal` для денег и процентов, `rs.getTimestamp(...).toLocalDateTime()`.
4. **В тесте** — только вызов DAO и `then(...)`. SQL в тесте не пишем.

```sql
-- Пилот по уникальному имени. Параметры: 1 = name.
select id, name, status, coverage_pct, created_by
  from pilot
 where name = ?
```

## Асинхронная запись — ждать условие, не паузу
```java
PilotRow row = await("пилот появился в БД").atMost(Duration.ofSeconds(15))
        .until(() -> pilotDb.findByName(name), Optional::isPresent)
        .orElseThrow();

await("запись в истории").atMost(Duration.ofSeconds(15)).untilAsserted(() ->
        then(pilotDb.history(row.getId()))
                .extracting(HistoryRow::getAction, HistoryRow::getActor)
                .containsExactly(tuple("CREATE", Cfg.get().adminLogin())));
```

## Что проверять в строке
- Поля, введённые пользователем, — литералами из кейса.
- Поля, которые вычисляет система: статус, автор, связи, суммы (`isEqualByComparingTo("15")` для `BigDecimal`).
- Историю и аудит: действие, автор, **ровно** сколько записей (`containsExactly`, а не «есть хотя бы одна»).

## Негатив «ничего не записалось»
Сначала докажи, что событие произошло (UI показал ошибку, запрос ушёл во внешнюю систему), потом проверяй отсутствие.
Иначе тест пройдёт и тогда, когда сохранение просто не успело начаться.

## Подготовка данных
По умолчанию — через API продукта (скилл `api-tests`, `createOk(...)`): проходят валидация, значения по умолчанию
и запись в историю. Прямой `INSERT` — только для состояний, недостижимых через продукт, с комментарием, какие правила
он обходит, с префиксом `AT-` и уборкой.

## Уборка
- Через API продукта, если есть удаление.
- SQL-уборка — образец `sql/pilot/delete_test_pilot.sql` (`where id = ? and name like 'AT-%'`).
- Историю изменений и аудит не удаляем: это журнал.

## Чек-лист
- [ ] Таблицы и колонки есть в `docs/db-schema.md`
- [ ] SQL в файле, колонки явно, параметры `?` с комментарием
- [ ] Проверки через `DbClient.readOnly()`
- [ ] Асинхронная запись ожидается `await`
- [ ] Проверены значимые поля, а не только наличие строки
- [ ] Уборка зарегистрирована до действия; запись — только по id и `AT-`
